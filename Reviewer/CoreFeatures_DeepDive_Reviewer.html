1. The Laundry Guard (Laundering Rules)

The master chore-tracking restriction preventing users from organizing or wearing outfits containing dirty clothes. This is the cornerstone feature bridging digital indexing to physical chores.

backend/wear_outfit.php backend/update_laundry_status.php assets/js/calendar.js

⚙️ Detailed Logic & Programmatic Execution

🔄
Status Shifting (The Trigger): When a user clicks "Wear" on an outfit in the calendar, Javascript intercepts the click via an Event Listener. It fires an asynchronous JSON fetch() containing the `outfit_id`. This PHP script unpacks the Outfit ID, queries the components, and executes a mass update query.
// PHP Execution Sequence inside wear_outfit.php $stmt = $pdo->prepare("UPDATE clothes SET status = 'Laundry' WHERE clothing_id IN (?, ?, ?) AND user_id = ?"); $stmt->execute([$top_id, $bottom_id, $shoe_id, $_SESSION['user_id']]);
🚫
The Cascade Block (The Restriction): What happens to *other* saved outfits? When rebuilding outfits dynamically during get_outfits.php, it checks if ANY component flags positive for status == 'Laundry'. The entire Outfit Object evaluates to a boolean payload: { "is_wearable": false }.
🛡️
UI Lockdown (Visual Protection): When calendar.js loops over the JSON, it detects is_wearable === false. It instantly manipulates the DOM directly:
// JS Execution inside calendar.js if (outfit.is_wearable === false) { outfitElement.classList.add('disabled-laundry'); outfitElement.removeAttribute('draggable'); // Destroys dragging capability }
✔️ Architectural Superiority & Security

By executing the Cascade Block securely inside the backend using explicit relational mapping, we prevent users from simply deleting the CSS class `.disabled-laundry` via Chrome Developer Tools. Even if a user hacks their browser to make the item draggable again, the backend's `save_schedule.php` restricts the placement natively.

4. Creating The Outfit Collage Image (Placeholder Logic)

How to physically render a full "Outfit Collage" without utilizing heavy software by perfectly stacking user clicks onto blank HTML template placeholders natively, whilst saving massive database storage.

⚙️ Step-By-Step Execution Architecture

🖼️
1. Preparing the HTML Empty Canvas: In AppPage/create.html, we don't start with clothes. We start with three distinct, carefully labeled Image slots loaded with an invisible or default "silhouette" graphic. Both IDs and `data-` attributes are empty.

👆
2. The JavaScript Memory & Click Intercept: Inside assets/js/create.js, whenever a user clicks on a shirt from their inventory sidebar, a specific function evaluates the image's category, finds the specific Placeholder ID in the DOM, and instantly swaps the src parameters!
// Inside assets/js/create.js function assignToCanvas(clothingId, imageUrl, category) { // 1. Identify which placeholder to overwrite let targetSlot = null; if (category === 'Top') { targetSlot = document.getElementById('canvas-top'); } if (category === 'Bottom') { targetSlot = document.getElementById('canvas-bottom'); } if (category === 'Shoes') { targetSlot = document.getElementById('canvas-shoes'); } // 2. Overwrite the visual image natively if (targetSlot) { targetSlot.src = imageUrl; // 3. Store the database ID in the HTML for 'Saving' later targetSlot.setAttribute('data-clothid', clothingId); } }
🎨
3. CSS Layer Stacking: In assets/css/style.css, we force the container to act like a mannequin perfectly combining the three overlapping parts using Flexbox. By setting flex-direction: column, raw rectangular image cards are natively forced to cascade vertically downwards cleanly. By omitting absolute positioning, if a Top's graphic is taller than expected, the Bottom graphic will smoothly flow underneath preventing visual breaks.
/* Inside assets/css/style.css */ .outfit-canvas-container { display: flex; flex-direction: column; /* Force Stack from Top to Bottom */ align-items: center; /* Center the mannequin */ position: relative; /* Allows Z-Index overlap */ } .outfit-canvas-container img { max-height: 200px; object-fit: contain; /* Prevents image stretching distortion */ margin-bottom: -15px; /* Pulls pieces tightly together overlapping */ }

4. Relational Database Logic (Massive Storage Optimization): Utilizing a PHP Graphic tool like `GD Library` to merge three JPGs requires 2MB+ of storage per outfit. MyFits circumvents asset bloating. It saves math mappings.

Because an entire stored Outfit is merely 3 integers (requiring ~12 bytes of database space), a user compiling 5,000 unique outfits physically requires 0 additional kilobyte storage capacities against server allocations!
✔️ Logic Review: Generating The Final Visual

When the user clicks "Save Outfit" in create.js, the Javascript exclusively pulls the three data-clothid properties off the HTML image tags, packages them into a JSON array, and sends it to save_outfit.php. By shifting the HTML image src properties via Javascript locally, we achieve an instantly refreshing collage canvas without any server delays or heavy image-processing.

6. The Outfit Catalogue Multi-JOIN SQL Matrix

The central database visual archive displaying mathematical pre-bundled combinations by explicitly referencing back into isolated inventory trees securely.

backend/get_outfits.php AppPage/mycloset.html assets/js/mycloset.js

⚙️ Detailed Logic & Programmatic Execution

📚
Mitigating The N+1 Query Problem: If we have 100 outfits, querying the `clothes` table individually for each subset would trigger 300 sequential database hits, immediately crashing the server. We bypass this entirely with a massive singular relational INNER JOIN map.
/* Explicit execution in get_outfits.php */ SELECT outfits.id, c1.image_path AS top_img, c1.status AS top_status, c2.image_path AS bot_img, c2.status AS bot_status, c3.image_path AS sho_img, c3.status AS sho_status FROM outfits INNER JOIN clothes c1 ON outfits.top_id = c1.id INNER JOIN clothes c2 ON outfits.bottom_id = c2.id INNER JOIN clothes c3 ON outfits.shoes_id = c3.id WHERE outfits.user_id = :user_id
🖥️
Resolving Structural JSON Payloads: Because the query successfully extracts the `status` checks for ALL THREE items simultaneously, PHP parses the logic natively: if ($top_status === 'Laundry' || $bot_status === 'Laundry' ...) { $is_wearable = false; }. It then packages the array. In assets/js/mycloset.js, it utilizes Template Literals to dynamically spawn <div class="outfit-card"><img src="${item.top_img}">...</div> natively onto the DOM mapping beautifully!

7. Catalogue Architecture: Automated Cascading Deletions

How the database handles destructive actions natively to protect the system from breaking if a user deletes a shirt that is secretly mapped to 55 different outfits!

backend/delete_clothes.php blueprint.sql

⚙️ Detailed Logic & Programmatic Execution

🧨
The Database Vulnerability Loop: Imagine a user creates an outfit using a Red Shirt. The next day, they click 'Delete' on the Red Shirt from their closet. If the backend simply deleted the shirt row, next time the Outfit Catalogue loaded, it would attempt to fetch a `top_id` that no longer existed, crashing the map!
🧬
Native MySQL ON DELETE CASCADE: Rather than writing complex PHP scripts to loop and find all dependent outfits, MyFits utilizes strict MySQL Relational Constraints within the initial Database Blueprint initialization.
/* Explicit execution in the root blueprint.sql */ ALTER TABLE outfits ADD CONSTRAINT fk_outfits_top FOREIGN KEY (top_id) REFERENCES clothes(clothing_id) ON DELETE CASCADE;
🛡️
Zero-Code Cleanup Process: Because of the `ON DELETE CASCADE` rule bound natively directly at the database level, the moment `delete_clothes.php` is executed by the user against the Red Shirt, MySQL acts as an autonomous guardian. MySQL instantly locates and purges every single Outfit Row and Scheduled Calendar date that ever utilized that specific shirt. The catalogue cleans up its own dependencies securely.
