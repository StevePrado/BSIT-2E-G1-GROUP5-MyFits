The Master Outfit Creator

An absolute deep-code breakdown: How 3 images combine visually, save systematically, and update dynamically in real-time.

The Complete Outfit Lifecycle

This document strictly answers the core engineering question: "How does the system physically 'create' an outfit, stack it together without breaking, and ensure live status updates still apply to it later?"

1

The Illusion of "Combining" Images

We never use heavy PHP Graphic Libraries to physically merge the three images into one. We create an optical illusion using HTML Frameworks and CSS Flexbox instead.

Step 1: The Invisible Canvas (create.html)
The screen starts entirely empty. We pre-build an invisible skeletal frame using three labeled HTML tags waiting to be manipulated.

<!-- Inside AppPage/create.html --> <div class="outfit-layer-container"> <!-- Default invisible placeholder images --> <img id="canvas-top" src="../assets/img/empty_top.png"> <img id="canvas-bottom" src="../assets/img/empty_bottom.png"> <img id="canvas-shoes" src="../assets/img/empty_shoes.png"> </div>
Why we use this: We assign explicit HTML IDs (`canvas-top`) so Javascript can target them like crosshairs later.

Step 2: Securing the Illusion (style.css)
If we just loaded three images next to each other, they would sit side-by-side. We MUST force them to stack vertically seamlessly mimicking a standing body.

/* Inside assets/css/style.css */ .outfit-layer-container { display: flex; flex-direction: column; /* FORCES images to stack downwards vertically */ align-items: center; /* Keeps them perfectly centered */ } .outfit-layer-container img { margin-bottom: -20px; /* Pulls the pieces tightly together, slightly overlapping */ object-fit: contain; /* Stops the images from looking stretched or fat */ max-height: 250px; }
Why we use this: flex-direction: column is the magic. It tells the browser compiler: "Take these 3 individual photos and crush them perfectly on top of one another." The user physically sees ONE outfit, but the browser is actually manipulating THREE disjointed assets.
2

Wiring The Live "Clicks"

How clicking a shirt in the sidebar magically makes the "One Outfit" update dynamically.

When you click an item, Javascript does two critical things: It updates the visual HTML canvas instantly, AND it saves the clothing_id into a global Javascript variable memory map.

// Inside assets/js/create.js let selectedTopId = null; let selectedBottomId = null; let selectedShoesId = null; function clickSidebarItem(clothingId, imageUrl, category) { if (category === 'Top') { selectedTopId = clothingId; // Save ID to JS memory securely! document.getElementById('canvas-top').src = imageUrl; // Swaps the image string natively! } else if (category === 'Bottom') { selectedBottomId = clothingId; document.getElementById('canvas-bottom').src = imageUrl; } }
Why we use this: Real-time User Experience! Changing an HTML src="..." string via Javascript causes the browser to download the image instantly without reloading the page. Because of the CSS flexbox rules we defined above, the new shirt instantly snaps into the exact correct stacked layer alignment.
3

Saving The Creation

We never upload a "new" combined picture to the server! Doing so would obliterate web storage limits. Rather, we save the math!

When the user clicks the final "Save Outfit" button, Javascript bundles those three specific integers we saved in Step 2, and fires an asynchronous POST request to PHP.

// Inside backend/save_outfit.php $stmt = $pdo->prepare(" INSERT INTO outfits (user_id, top_id, bottom_id, shoes_id) VALUES (?, ?, ?, ?) "); $stmt->execute([ $_SESSION['user_id'], $postData['top_id'], $postData['bottom_id'], $postData['shoes_id'] ]);
Why we use this: The `outfits` table literally only contains numerical numbers. For example: Outfit #15 simply says: (Top #12, Bottom #4, Shoes #77). This takes up approximately 20 bytes of database space, making the app capable of storing millions of outfits without bogging down server SSDs.
4

Sustaining Live Real-Time Dependencies

When you wash a piece of clothing, why does the entire Outfit physically know it's "Dirty" on the screen?

Because we explicitly did not bundle the images into one merged file, the Outfits are strictly tied to the live health of the original clothes! Every time we render the "Outfit Catalogue", we execute an advanced SQL JOIN that acts like a live stethoscope listening to the original parts.

-- Inside backend/get_outfits.php SELECT outfits.id, c1.image_path as top_img, c1.status as top_status, c2.image_path as bot_img, c2.status as bot_status, c3.image_path as shoes_img, c3.status as shoes_status FROM outfits INNER JOIN clothes c1 ON outfits.top_id = c1.id INNER JOIN clothes c2 ON outfits.bottom_id = c2.id INNER JOIN clothes c3 ON outfits.shoes_id = c3.id
How the Magic works: If a user puts their white shirt in the laundry, `update_laundry_status.php` flips the original white shirt row to 'Laundry'. Because our `get_outfits.php` query performs an `INNER JOIN` bridging `outfits` strictly back to `clothes`, the Javascript dynamically pulls down the live top_status variable as 'Laundry'!

The Result: The entire Outfit object inherits the 'Laundry' warning instantly. Javascript loops over it and applies the red overlay. The system stays permanently synced mathematically without requiring complex backend cleanup loops!
