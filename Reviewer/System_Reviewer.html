The Complete System Architecture, Flow & Codebase Reviewer Deep Dive

1. System Overview

MyFits is an end-to-end digital wardrobe management system. Designed to seamlessly merge fashion indexing with chore tracking (laundry cycles), it provides a robust, synchronized platform where clothing status dictates outfit availability. The system is built with separation of concerns in mind: API logic on the backend, interactive DOM rendering on the frontend, and strict relational data rules in the database.

PHP (Backend API) MySQL (Relational DB) JavaScript / DOM (Client Side) Bootstrap 5 / Vanilla CSS (UI Layer)
Why this tech stack?
  • PHP: Provides robust, session-based Server-Side logic. It strictly acts as an API layer echoing JSON to the frontend, allowing for a decoupled architecture where the UI can evolve without breaking server logic.
  • MySQL: Ensures absolute data integrity through Relational Foreign Keys, meaning an outfit cannot legally exist in the DB if the original clothing items have been deleted.
  • JavaScript: Handled client-side to prevent unnecessary page reloads, providing a "Single Page Application (SPA)" feel by manipulating DOM elements asynchronously (e.g., dragging items into the calendar, filtering clothes instantly).

2. Database Schema Architecture

The system utilizes a highly normalized 4-core-table architecture designed specifically to manage complex cascading dependencies (e.g., deleting a user deletes their clothes, which deletes their outfits, which deletes their schedule).

Table Name Detailed Description & Motivation Primary Key (PK) Foreign Key (FK) Dependencies
users The authoritative identity table. Stores authentication data, securely hashed passwords, profile emails. Everything in the app belongs to an individual user via this table. user_id None - This is the root node.
clothes The raw inventory grid. Tracks every individual piece (e.g., a specific red shirt). It records image paths, 'status' (ready vs. laundry), and assigned categories. id / clothing_id user_id (Belongs to specific User)
outfits The combinatorial table. It doesn't upload duplicate images; rather, it clusters references by storing the IDs of a Top, Bottom, and Shoes to map them into one unified "Outfit". id / outfit_id user_id (Security binding)
top_id, bottom_id, shoes_id (Mapped to clothes table)
schedule The temporal binding table. Maps an existing Outfit to a specific chronological Date. Also tracks boolean states like whether the look has physically "been worn" today. id / schedule_id user_id (Security binding)
outfit_id (Mapped to outfits table)

3. System Flow & Lifecycle

A. The "Cycle of Wear" Implementation Logic

This is the core business logic of the application. It prevents the user from organizing outfits using dirty clothes.

1
Inventory Registration: User uploads a shirt to the Closet. System assigns it status = 'Ready'. It is now eligible to be used.
2
Creation Phase: The user bundles the shirt via `create.js` into an Outfit. The UI successfully renders the Outfit.
3
Deployment: The Outfit is placed on the Calendar. On the requested date, the user clicks "Wear Look". This triggers wear_outfit.php.
4
Status Cascade: The backend isolates all components of that Outfit, forcing their DB status to 'Laundry'. Any other saved Outfit that also uses that same shirt instantly becomes automatically blacklisted/disabled in the UI.
5
Revival: The user visits the 'Laundry Basket' view, triggering update_laundry_status.php, washing the clothes, reverting them to 'Ready'. The outfits become available again.

4. Exhaustive File Architecture Review

Detailing *every* file, what it structurally aims to achieve, and precisely why it was implemented.

Directory: /includes/ (Core Configuration Middleware)
db_connect.php
What it does:

Establishes an active PDO instance securely linking the server to the MySQL database.

Why it is crucial:

By centralizing the connection, we uphold DRY (Don't Repeat Yourself) principles. If the server credentials change, only this file is updated. It configures PDO err-modes to throw Exceptions strictly, avoiding silent failures.

session_guard.php
What it does:

Checks if `$_SESSION['user_id']` exists. If not, it halts script execution (`die()`) and echoes an unauthorized error.

Why it is crucial:

It acts as the primary Bouncer. Included at the literal top of every single protected PHP file, it guarantees malicious actors cannot curl/hit API endpoints to download inventory logic without carrying a valid browser session cookie.

check_db.php & test_pdo.php & get_tables.php
What it does:

Raw diagnostic scripts meant for pinging the database health and dumping active relational schemas.

Why it is crucial:

Used strictly for deployment monitoring. Guarantees the cloud environment successfully migrated SQL structures before production launch.

Directory: /backend/ (REST-Style Controller API)
Authentication Module
login_process.php
What it does:

Validates login forms against the DB, uses `password_verify()`, and binds `$user_id` to system memory via session cookies.

Why it is crucial:

Without this, the firewall logic blocks everything. Secures user accounts via irreplicable Bcrypt hash cross-matching.

signup_process.php
What it does:

Registers new rows in `users`. Salts plain-text passwords and enforces email uniqueness constraint.

forgot_process.php & support_process.php
What it does:

Manages forgotten accounts flow & records customer support tickets into internal system logic.

Inventory Modules (The Closet Logic)
get_clothes.php
What it does:

Echoes pure JSON formatting of ALL inventory bound strictly to the active SESSION user ID. Takes optional GET parameters to filter categories.

Why it is crucial:

The JS UI cannot talk to SQL. This file acts as the bridge. It enforces data isolation—users *cannot* fetch ID profiles they don't own.

add_clothes.php
What it does:

Ingests POST form data, validates MINE types of uploaded images (`.jpg`, `.png`), shifts the file securely to `/uploads`, and enters the routing record to the DB.

update_clothes.php & delete_clothes.php
What it does:

Allows granular mutations (updating labels) and secure Hard-Deletion. If a piece dies, foreign keys destroy dependent outfits.

update_laundry_status.php
What it does:

A binary toggle endpoint specifically shifting a clothe's exact database cell between 'Ready' and 'Laundry'.

Why it is crucial:

This micro-service handles the entire 'Basket' view functionality asynchronously, reviving outfits universally.

Outfit & Calendar Managers
get_outfits.php & get_outfit.php
What it does:

Renders composite JSON arrays. Instead of fetching raw clothes records, it fetches associative joins connecting the Top, Bottom, and Shoe images automatically into bundled nodes.

save_outfit.php & delete_outfit.php
What it does:

Persists the mathematical combination of IDs. Deleting it merely severs the bundle—it does NOT delete the actual clothing.

wear_outfit.php
What it does:

A mass-trigger cascading algorithm. Receives an Outfit ID, reads its component Clothes IDs, and runs bulk SQL `UPDATE` loops placing those parts into out-of-order dirty states.

Why it is crucial:

It is the execution layer of the app's real-time chore architecture.

get_schedules.php / save_schedule.php / delete_schedule.php
What it does:

A suite of endpoints strictly managing DateTime mappings to Outfits on the calendar grid.

migrate_db.php & migrate_exclusions.php
What it does:

Internal execution algorithms used to configure database scaffolding or patch alterations via PHP runtime logic safely.

5. Key System Features Defined

Laundry Guard Algorithm

An embedded logic flow blocking bad interactions. If the core DB notes a clothing part is 'Laundry', any associated Outfits querying that clothing part will trigger a flag. The JS then dynamically dims the outfit box, adds an overlay, and disables "Wear" buttons, physically restricting logic errors without frustrating the user.

Dynamic SPA Filtering

Real-time catalogue interaction. Keystrokes bound to search interfaces asynchronously mutate the DOM Array using Vanilla JS array methods (like `.filter()` and `.includes()`). This yields lightning-fast closet sorting completely detached from heavy server processing.

Visual Auth Visibility

A necessary UX interaction pattern. Bound to the 'Eye' vector graphic on secure forms, JS detects clicks to instantly flip the HTML DOM input property from `type="password"` (hidden dots) to `type="text"` (bare text) preventing login confusion loops.

6. Core Security Implementations

Every aspect of the platform's backend infrastructure is engineered to protect user matrices against common vulnerability vectors.

  • Strict SQL Parameterization: There is absolutely zero direct string-concatenation within queries. Instead of writing SELECT * WHERE id = $id, the PDO engine uses WHERE id = ? and securely binds variables natively, neutralizing SQL injection threats fundamentally.
  • Cryptographic Storage: User passwords are encrypted through PHP's native password_hash() system utilizing the Bcrypt algorithm and salt randomization. Even partial database leaks yield zero plain-text password compromise.
  • Isolated Data Contexts: Due to session_guard.php, every query forcibly filters results strictly through the active $_SESSION['user_id']. A user manipulating client-side fetches physically cannot scrape profiles owned by neighbor ID ranges.
  • Input Scrubbing: Malicious script payloads passed into "Name Outfit" boxes are intrinsically scrubbed or encoded, blocking XSS (Cross Site Scripting) payloads from executing upon UI rending.
