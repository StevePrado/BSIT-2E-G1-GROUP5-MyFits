MyFits Frontend Architecture

Deep Dive Reviewer: How the UI Functions & How We Do It

1. The Frontend Strategy Overview

The MyFits frontend is designed to feel like a lightning-fast Single Page Application (SPA), despite being built on multiple HTML files. To achieve this, the frontend never relies on PHP to render the HTML structure. Instead, the HTML files act as empty "canvases," and the core Vanilla JavaScript files dynamically paint the data onto the screen by manipulating the Document Object Model (DOM) after fetching data silently in the background.

2. HTML Architecture: The Visual Skeletons

Every HTML file in the project purposefully lacks data upon load. They exist strictly to provide structural container IDs (e.g., id="closet-grid") for JavaScript to target.

Directory: /AppPage/ (Secured User Endpoints)
mycloset.html
What this does:

Provides the structural layout for the primary inventory view, including the Sidebar Navigation, the Top Navbar search bar, and the main Content Area.

How this functions:

It contains distinct HTML elements like <select id="categoryFilter"> and a unified empty <div id="clothes-container"></div>. These IDs are explicit hooks. HTML doesn't do the filtering—it just provides the interactive input tags that JS listens to. We structured the UI using Bootstrap 5's Grid System (container, row, col-md-4) to ensure that when JS drops 30 items into the container, they automatically wrap securely on mobile devices.

create.html & edit.html
What this does:

Houses the Layout for the "Outfit Builder Playground".

How this functions:

The HTML explicitly divides the screen into two portions: an inventory sidebar and an "Outfit Canvas". Inside the Canvas, we hardcoded three empty placeholder boxes: [Top], [Bottom], [Shoes] constraints. By physically segregating the HTML like this, it gives the user an intuitive visual boundary showing they cannot add two shirts to one outfit layout.

calendar.html
What this does:

Provides the framework for the scheduling UI.

How this functions:

Very minimal HTML. It simply defines an empty container <div id="calendar"> and a sidebar <div id="outfits-list">. The HTML forces a flexbox structure so the calendar spans the right side of the screen extensively (taking up 80% width) so users have a wide visual margin to drop items.

support.html
What this does:

Holds the forms required to submit bug reports directly from the authenticated dashboard.

How this functions:

Provides a clean text-area field. The key here is the <form> tag purposefully lacks an action="submit.php" attribute, meaning pressing enter won't refresh the page, allowing JS to intercept it gracefully.

Directory: /MarketingPage/ (Public Funnels)
index.html, about.html, services.html
What this does:

The marketing suite focused solely on conveying trust, features, and leading the user to register.

How this functions:

These files rely heavily on CSS animations and Bootstrap Hero-components. Because no private data is shown here, they are populated with hard-coded text and optimized entirely for fast loading speeds and SEO mapping.

gallery.html
What this does:

An emulation sandbox so potential users can "test drive" the application logic before handing over an email address.

How this functions:

The HTML mirrors `mycloset.html` visually, but operates in a sealed environment triggering specific Call-To-Action modals when users try to 'save' a look.

signup.html, login.html, forgot.html
What this does:

The gateway input forms.

How this functions:

These employ specific HTML5 input types (e.g., type="email" over type="text") immediately triggering the browser's built-in email domain validations before JS even gets a chance to see it, ensuring minimal error traffic.

3. JavaScript Functionality: The Core Brain

This section explores exactly what the client-side JavaScript is doing under the hood, how the functions operate, and why we structured it this way.

Directory: /assets/js/
mycloset.js
What this does:

It acts as the inventory rendering engine. It retrieves your clothing items from the database and visually draws them into the grid. It also powers the live search and category buttons.

How this functions:

Upon page load, a fetch() request is immediately fired to get_clothes.php. It receives a JSON string back. The JavaScript then parses this JSON and loops through it using array iteration (like .forEach() or .map()). For each item, it constructs raw HTML strings (e.g., <div class='card'>...</div>) and injects them violently fast into the innerHTML of the closet container. For the live search, an Event Listener monitors keystrokes (keyup) and instantly filters the active JSON array, redrawing only the matching cards.

Why we do this:

By filtering data via JavaScript arrays locally in the browser, we avoid sending a new request to the server every time a user types a letter. This saves massive server bandwidth and makes the search feel instantaneous (zero latency).

create.js & edit.js
What this does:

Powers the interactive "Outfit Canvas." It restricts the user to picking exactly one Top, one Bottom, and one pair of Shoes, and then bundles them into a specific outfit ID.

How this functions:

When a user clicks a clothing item on the canvas, an Event Listener reads the data-id attribute attached to that specific HTML image. The JS actively stores these variables in browser memory (e.g., let selectedTop = 14;). It physically moves or highlights the chosen DOM node to show selection. Finally, when "Save" is clicked, JS bundles these variables into a FormData object and ships it off via an asynchronous Ajax POST request to save_outfit.php.

Why we do this:

We do this to provide real-time visual feedback. Users need to visually see their outfit combo before confirming. Holding the data state in JS memory allows endless mixing-and-matching without constantly hitting the database.

calendar.js
What this does:

Calculates the monthly grid metrics, loads saved outfits to their assigned dates, handles Drag-and-Drop functionality, and operates the "Laundry Guard" UI mechanism.

How this functions:

The Grid: It uses JavaScript's built-in Date() object to figure out what day the 1st of the month lands on, dynamically looping to create 30/31 HTML grid boxes.
The Dragging: HTML5 Drag APIs are utilized. An outfit div is marked draggable="true". When dropped into a calendar date box, JS reads the Outfit ID and the Date ID, then silently pings the database to record the link.
Laundry Guard: Before allowing a user to click "Wear", the script checks the statuses inside the outfit JSON. If it detects status === 'Laundry', JS targets that specific DOM element and strips the "wear" buttons away, substituting them with a faded semi-transparent CSS class.

Why we do this:

A calendar heavily implies interactivity. Forcing a user to fill out a dropdown form to assign an outfit to a date is clunky. Drag-and-drop JavaScript provides a modern, tactile mobile-friendly UX.

login.js & signup.js
What this does:

Acts as the frontline security guard, preventing bad data from ever leaving the browser. Handles the "Eye" toggle for password visibility.

How this functions:

It intercepts the HTML form's default submit event by calling e.preventDefault(). It then checks if the password length is > 6 characters, and if the confirm password field perfectly matches. If not, it dynamically manipulates CSS classes to reveal red alert text natively on the document.
The password visibility simply toggles the DOM property from document.getElementById('pass').type = "password" to "text" when the eye icon is clicked.

Why we do this:

Server requests take time. If a user typoes their password confirmation, sending that form all the way to the PHP server just to have it rejected creates a terrible 3-second delay for the user. Client-side JS validation fails instantly, creating a vastly superior UX.

forgot.js & support.js
What this does:

Process forms explicitly detached from main data loops. forgot.js processes verification chains, and support.js routes UX feedback loops.

How this functions:

Intercepts form submissions via Event Listeners, halts reload, bundles input values, and sends them. Upon success, they swap the DOM visibility properties (display: none;) revealing "Thank you!" screens natively on top of the old forms.

Why we do this:

Provides a silky smooth conclusion. Redirecting a user to a completely text-bare "Success.php" page after a bug ticket submission looks unprofessional. Fading out the prompt dynamically on the same page is modern UX practice.

gallery.js & gallery_demo.js
What this does:

Simulates the exact behavior mechanics of mycloset.js without actually hooking up to the PHP endpoints or database structures.

How this functions:

These files declare long static JavaScript arrays (storing fake image links and tags) at the absolute top of the file as constants. It uses pure Javascript Logic arrays to render the visual UI to mimic the active dashboard perfectly.

Why we do this:

To safely provide potential users traversing the Marketing funnel a true 1:1 sandbox experience showing how clothes sorting features operate, all without giving them permission access to our inner server data flow APIs.

4. How Core UI Mechanisms Work

The "AJAX" Non-Refresh Method

What it is: Every time you wear an outfit or add laundry, the page doesn't blink or reload.

How we do it: We exclusively use the modern fetch() API. When a button is clicked, JS sends a silent packet of data to the server behind the scenes. When the server responds with "Success", the JS manually deletes or updates that specific HTML element from the screen using element.remove() or element.classList.add('dirty').

The UI Badging System

What it is: The small "Ready" or "In Laundry" tags floating securely over the clothing cards.

How we do it: We rely on CSS "Absolute Positioning". The parent clothing card is set to position: relative;, and the badge span is set to position: absolute; top: 10px; right: 10px;. JavaScript reads the database status, and if it says 'Laundry', it injects the red HTML badge into this absolutely positioned slot.
