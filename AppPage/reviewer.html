1. Database Design & Normalization (15% + 10%)
How did you apply normalization to your database design to prevent repeating columns?
File: includes/blueprint.sql
We designed our relational database using multiple tables to eliminate data redundancy entirely. This implies our database sits in what is known as 3rd Normal Form (3NF).

Detailed Explanation: Instead of making one giant table that saves a user's name, the color of their shirt, and the day they wore it all in one row (which causes massive duplication), we split them up.
  • We have a users table for credentials.
  • We have a clothes table for the items themselves.
  • We have an outfits table. The outfits table does NOT save the color or image of the shirt again; it simply saves the Foreign Key ID (e.g., top_id = 15) pointing back to the clothes table.
  • Both tables point back to the users table via user_id.
If asked by the Professor: "Normalization simply means we don't repeat data. If I own a black shirt, its image and color are stored exactly ONCE in the database. Outfits and Schedules just point to its ID."
How does the Calendar Scheduling connect to Outfits without duplicating data?
File: includes/blueprint.sql & backend/save_schedule.php
We use a dedicated junction table called schedules. It links an existing outfit_id (foreign key) to a specific scheduled_date.

What it does: This allows a single outfit (like "My Sunday Best", ID: 10) to be worn repeatedly across 50 different calendar days without us having to copy the outfit 50 times in the database. We just create 50 schedule rows that all point back to Outfit ID 10.
2. Security, User Roles & SQL Validation (10% + 15%)
How do you protect the database from Hackers trying a "SQL Injection" attack?
File: backend/save_outfit.php
We utilize Prepared Statements across all of our PHP files. A prepared statement forces the database engine to treat user input strictly as text, neutralizing any malicious code they try to type into a form. 
// Notice how we use Question Marks (?) instead of actual variables in the query!
$stmt = $conn->prepare("INSERT INTO outfits (user_id, name, top_id, bottom_id, shoes_id) VALUES (?, ?, ?, ?, ?)");

// Then we 'bind' the variables later. The 'isiii' tells MySQL exactly what to expect: 
// Integer, String, Integer, Integer, Integer. This makes injection impossible.
$stmt->bind_param("isiii", $user_id, $name, $top_id, $bottom_id, $shoes_id);
$stmt->execute();
If asked by the Professor: "We never paste variables directly into SQL strings. We prepare the SQL statement with '?' marks first, and then bind the parameters safely. This makes SQL injection impossible because the database engine refuses to execute the variables as code."
How did you implement Security, User Access, and Administrator Roles?
File: backend/get_report.php & backend/login_process.php
First, for baseline security, passwords are never stored as plain text. When a user signs up, the system runs password_hash(). When they log in, it uses password_verify() to securely match the hash.

User Roles (The Advanced Feature): The database users table has a column called role which is an ENUM set to either 'user' or 'admin'.
Our Report Generation API strictly blocks normal users via server-side checks. If someone is not an admin, they are forcefully denied. 
// The Server checks the database for the current logged-in user's role
$roleStmt = $conn->prepare("SELECT role FROM users WHERE id = ?");
$roleStmt->bind_param("i", $user_id);
$roleStmt->execute();
$roleResult = $roleStmt->get_result()->fetch_assoc();

// If they are NOT an admin, block them completely and exit the script
if (!$roleResult || $roleResult['role'] !== 'admin') {
    echo json_encode(["status" => 403, "message" => "Access Denied: You do not have administrator privileges."]);
    exit();
}
3. Advanced Feature: Database Transactions (ACID) (10%)
Can you explain why you needed a complex Database Transaction, and where it is in the code?
File: backend/wear_outfit.php
The Problem: When a user marks an outfit as "Worn" inside our Calendar, multiple things must happen in the database instantly:
1. The specific calendar day must be marked as worn.
2. The Top, the Bottom, and the Shoes must all get +1 to their wear_count metric.

The Solution (Transactions): We wrapped these multiple UPDATE queries inside a single Database Transaction. If our server crashes after updating the Top but before updating the Bottom, the system's inventory metrics would be permanently corrupted (mismatched wear counts).

The commit() statement ensures that either ALL the updates lock into the database together, or if there is an error, rollback() reverses them entirely (like nothing ever happened). 
// 1. Start the Transaction. 
// Tells MySQL: "Pause saving permanently until I say we are done."
$conn->begin_transaction();

try {
    // Action 1: Mark schedule row as worn
    $stmt1 = $conn->prepare("UPDATE schedules SET is_worn = 1 WHERE id = ?"); 
    
    // Action 2: Increment the wear count for all 3 clothing items
    $stmt2 = $conn->prepare("UPDATE clothes SET wear_count = wear_count + 1 WHERE id IN (?, ?, ?)"); 
    
    // Action 3: Finalize and save everything to the database together
    $conn->commit(); 
    
} catch (Exception $e) {
    // If ANYTHING fails, abort and delete the partial updates safely!
    $conn->rollback(); 
    echo json_encode(["status" => 500, "message" => "Transaction failed, changes rolled back."]);
}
4. Advanced Feature: Materialized Views + Report Generation (10% + 15%)
How did you optimize generating Reports for the Administrator?
File: includes/run_advanced_migration.php & backend/get_report.php
The Problem: When an Admin clicks "System Report" to see how many clothes and outfits every user has, running massive SQL JOIN and COUNT() aggregations across thousands of rows can significantly slow down the PHP server.

The Advanced Solution (MySQL View): Instead of forcing PHP to do the math, we created a **MySQL View** named user_inventory_report directly inside the database. A View is like a saved, virtual, self-updating spreadsheet. The Database engine manages the complex aggregation logic behind the scenes.

Because of this View, our PHP API endpoint does barely any work. It simply asks the database to read from the View instantly. 
// 1. The SQL we used to CREATE the virtual view inside the Database:
CREATE OR REPLACE VIEW user_inventory_report AS 
SELECT 
    u.id AS user_id, 
    u.fname AS user_name,
    COUNT(DISTINCT c.id) AS total_clothes, 
    COUNT(DISTINCT o.id) AS total_outfits
FROM users u
LEFT JOIN clothes c ON u.id = c.user_id
LEFT JOIN outfits o ON u.id = o.user_id
GROUP BY u.id;

// 2. The simple, incredibly fast query inside get_report.php:
// We don't need JOINS here anymore, the View handled it for us!
$query = "SELECT * FROM user_inventory_report";
$result = $conn->query($query);
5. Client-Server Architecture (10%)
Walk me through the Client-Server flow. What happens behind the scenes when a user clicks "Add Clothes"?
Files: AppPage/mycloset.html -> assets/js/mycloset.js -> backend/add_clothes.php
This demonstrates a perfect 3-Tier Architecture workflow:

  1. Step 1 (The Client / Browser): The user selects a photo and fills out the HTML form in mycloset.html. When they hit save, our Javascript (mycloset.js) prevents the page from reloading. It packages the image and form data into a heavy payload and sends an HTTP POST request (AJAX/Fetch) across the network.
  2. Step 2 (The Server / PHP API): The API endpoint (add_clothes.php) receives the network request. The Server first acts as a security guard, reading the $_SESSION['user_id'] to prove the user is logged in. It then securely moves the physical image file into our server's /uploads folder. Finally, it formulates the secure SQL statement.
  3. Step 3 (The Database): The PHP server executes the parameterized INSERT INTO clothes command upon the MySQL database. The database locks in the row data.
  4. Step 4 (The Response): The database returns a "Success" flag to PHP. PHP wraps that flag in a JSON object and echoes it back to Javascript. Javascript reads the successful JSON response and instantly draws the new clothing image onto the screen, providing a real-time, App-like experience for the user.
If asked by the Professor: "Our client is decoupled from our database. HTML never talks directly to MySQL. Javascript talks to PHP via JSON, and PHP talks to MySQL. This ensures security and scalability."
